# Движки магазинов

[English](../en/engines.md) · **Русский**

Для кого: владелец магазина на одном из поддерживаемых движков, которому нужен готовый `store.toml` без написания адаптера. `shopmcp scaffold` определяет движок (или берёт его из `--engine`) и пишет подходящие `[adapter]` и `[cart]` из пресета (`src/shopmcp/engines.py`).

Содержание: [Поддерживаемые движки](#поддерживаемые-движки) · [Scaffold](#scaffold) · [Определение движка](#определение-движка) · [Что заполнить вручную](#что-заполнить-вручную) · [form_post: бета](#form_post-бета) · [Заметки по движкам](#заметки-по-движкам)

## Поддерживаемые движки

Десять пресетов. Каждый пресет — дефолт, которому ничего не нужно ставить на стороне магазина; модуль или сниппет в магазине даёт корзину получше (стратегия `receiver`, см. [cart-receiver.md](cart-receiver.md)) и записывается в конфиг комментарием `Апгрейд:`.

| `--engine` | Каталог (адаптер / фид) | Корзина (стратегия) | Статус |
|---|---|---|---|
| `shopify` | своего адаптера нет: фид Google Merchant из приложения (`kind = "feed"`) | `url_template`, `https://<host>/cart/{items}?storefront=true`, позиции `{id}:{qty}` | Готов; вид id фида `shopify_<CC>_<товар>_<вариант>` живьём не проверен |
| `woocommerce` | адаптер `woocommerce` (Store API без ключей), фид не нужен | `link_list` со ссылкой-добавлением на каждую позицию; на WooCommerce 10+ — закомментированный `url_template` `/checkout-link/?products={items}` | Готов |
| `ecwid` | фид Google Merchant из настроек Ecwid | `json_fragment`, корзина во фрагменте URL; вариант `base64` для магазина на сайте Wix | Готов; формат фида Ecwid не проверен |
| `bitrix` | фид YML | `link_list` с `{url}?action=ADD2BASKET&id={id}&quantity={qty}` | Готов |
| `prestashop` | фид Google Merchant (модуль фида) | `link_list` с `?add=1&id_product=…&id_product_attribute=…&qty=…` | Готов |
| `opencart` | фид YML (модуля) | `link_list`, ссылки на карточки | Готов |
| `magento` | фид Google Merchant (расширения) | `link_list`, ссылки на карточки | Готов |
| `tilda` | фид YML (`/tstore/yml/<hash>.yml`) | `link_list`, ссылки на карточки | Готов |
| `insales` | фид YML | `link_list`, ссылки на карточки; `form_post` (режим `single`) — закомментированной альтернативой | Готов; `form_post` — **БЕТА**, см. [ниже](#form_post-бета) |
| `shop_script` | фид YML | `link_list`, ссылки на карточки; `form_post` (режим `chain`) — закомментированной альтернативой | Готов; `form_post` — **БЕТА**, см. [ниже](#form_post-бета) |

OpenCart и Magento на `form_post` не стоят: их корзины не принимают межсайтовый POST (OpenCart отвечает сырым JSON, Magento требует `form_key`), поэтому пресет отдаёт ссылки на карточки, а апгрейд модулем — `receiver`.

«Готов» значит: код и тесты есть; живая проверка ссылок корзины на настоящих магазинах — отдельный этап, здесь она не заявляется.

## Scaffold

```bash
uv run shopmcp scaffold my-shop --site https://shop.example
uv run shopmcp scaffold my-shop --site https://shop.example --engine woocommerce
uv run shopmcp scaffold my-shop --site https://shop.example --engine prestashop --feed https://shop.example/feed.xml
```

| Параметр | Назначение |
|---|---|
| `--site URL` | Сайт магазина, обязателен. Становится `site`; ссылки корзины строятся на его хосте. Для движка в подкаталоге (`https://shop.example/shop`) путь сохраняется в ссылках |
| `--engine` | Одно из десяти имён выше. Пропускает определение |
| `--feed` | Путь или `https://`-URL фида для `[adapter]`. Игнорируется (с пояснением) движками, адаптер которых фид не читает (`woocommerce`) |
| `--prefix`, `--locale` | Как в [quickstart.md](quickstart.md#свой-магазин) |

Команда пишет `stores/<store_id>/store.toml` в текущем каталоге и не перезаписывает существующий файл. Комментарии в файле на двух языках; строки с пометкой `EDIT` — ваши. Без `--engine`, если движок не определён, файл получается общим: фид YML и ссылки на карточки.

## Определение движка

Без `--engine` scaffold смотрит на сайт (`src/shopmcp/detect.py`):

- **Только GET**, без кук и без тела запроса. Не больше 8 запросов по 10 с, тело ответа обрезается на 512 КБ, не больше 3 редиректов. User-Agent — `shopmcp-scaffold/<версия>`.
- Читает главную страницу, затем несколько дешёвых подтверждающих запросов (например, Store API WooCommerce и GraphQL Magento).
- Признак либо решающий (так отвечает только этот движок), либо намёк (встречался у движка, но тема или CDN могут дать то же). Один решающий признак даёт движок. Один намёк — движок с предупреждением.
- **Два движка с решающими признаками или несколько намёков дают кандидатов и не дают выбора**: сводка перечисляет их, выберите один через `--engine`.
- **«Не определено»** — нормальный ответ, а не ошибка. Он печатается с причиной, когда сайт недоступен, когда главная закрыта антиботом или правилом доступа (HTTP 401, 403, 429, 503 или страница-проверка) либо когда признаков нет. Это значит «неизвестно», а не «движок не поддерживается»: задайте `--engine` вручную. Типичное слепое пятно — Ecwid: его виджет часто подгружается скриптом, которого простой GET не исполняет.
- На известные ловушки выводятся предупреждения: Битрикс за витриной на Next.js (ссылки-добавления не работают, `line_template` убирается), Tilda без блока магазина, PrestaShop без `var prestashop` (1.6 или нестандартная тема).

Сводка после запуска перечисляет движок, признаки и что вписать:

```text
engine: Shopify (--engine)
cart: url_template; Shopify publishes its own store MCP: no catalog adapter, only the cart link here. …
fill in by hand (lines marked EDIT): brand, instructions, server.public_url,
  conformance.sample_query, adapter.feed, adapter.cart_ref
created stores/demo2/store.toml; edit the lines marked EDIT
```

## Что заполнить вручную

Всегда: `brand`, `instructions`, `server.public_url`, `conformance.sample_query` (scaffold пишет `CHANGE-ME`, поэтому проверка красная, пока вы его не замените). По движкам — строки с пометкой `EDIT`:

| Движок | Ещё заполнить |
|---|---|
| `shopify` | `adapter.feed` (фид Google Merchant из приложения); сверить `pattern` в `[adapter.cart_ref]` с `g:id` своего фида |
| `woocommerce` | больше ничего; если нужна корзина одной ссылкой — подтвердить версию WooCommerce и раскомментировать альтернативный блок `[cart]` |
| `ecwid` | `adapter.feed`; опции товара для корзины — в `options` секции `[adapter.cart_ref]` |
| `insales` | `adapter.feed`; для `form_post` — `SHOPMCP_CART_SECRET` в окружении |
| `shop_script` | `adapter.feed`, `[adapter.cart_ref]` (как id фида делится на товар и SKU); для `form_post` — `SHOPMCP_CART_SECRET` |
| `bitrix` | `adapter.feed`; на headless-витрине убрать `line_template` (scaffold делает это сам, если распознал такую витрину) |
| `prestashop` | `adapter.feed`, `[adapter.cart_ref]` для id вида `12-34`, `cart.line_template`: путь корзины зависит от языка витрины (`cart`, `panier`, …) |
| `opencart`, `magento`, `tilda` | `adapter.feed` |

`cart.secret` — только ссылка `${ENV}`, не литерал, и не короче 32 байт. Справочник по полям: [configuration.md](configuration.md#cart).

## form_post: бета

`form_post` — корзина для InSales и Shop-Script, которые принимают товары в корзину только POST-ом. Это **БЕТА**, поэтому scaffold пишет рабочей корзиной ссылки на карточки (`link_list`), а блок `form_post` — закомментированным. Чтобы включить: раскомментируйте блок, задайте `SHOPMCP_CART_SECRET` (не короче 32 байт) и запустите `shopmcp check`.

### Как это работает

Ссылка на корзину — `<origin из server.public_url>/cart/h/<подписанный токен>` ([формат токена](cart-receiver.md#формат)). Сервер корзин не хранит: позиции лежат в токене. Страница по ссылке отправляет позиции в магазин POST-ом из браузера покупателя, поэтому магазин видит его собственные куки:

- `single`: одна форма со всеми позициями, отправляется при загрузке (InSales `/cart_items`).
- `chain`: форма на каждую позицию. Магазин отвечает на каждый POST редиректом на страницу, с которой пришёл браузер, и страница отправляет следующую позицию; после последней уходит на `finish_url` (Shop-Script `/cart/add/`). Это работает, потому что страница просит полный `Referer` (`Referrer-Policy: unsafe-url`), и магазин возвращает браузер на неё. Запасной путь не нужен. CSP страницы разрешает в `form-action` магазин и `'self'`: без `'self'` Chromium блокирует возврат на страницу, и цепочка встаёт после одной позиции.
- Без JavaScript те же формы показываются кнопками («Добавить позицию 2 из 3»).
- `action` и `finish_url` берутся только из `store.toml`, никогда из токена; истёкшая или повреждённая ссылка даёт страницу `400` со ссылкой на сайт.

Повторное открытие той же ссылки (другая вкладка, кнопка «Назад») позиции второй раз не добавляет: страница находит свою отметку в хранилище браузера, пишет, что товары уже отправлены, и предлагает ссылку в корзину и кнопку **Добавить ещё раз**. Если хранилище заблокировано (приватный режим), страница отправляет позиции при каждом открытии.

### Где размещать сервер

Исход зависит от того, отправит ли браузер куку корзины магазина вместе с POST. Это решают атрибут куки `SameSite` и то, на сайте ли магазина находится страница. Сайт — это регистрируемый домен по Public Suffix List: `mcp.shop.example`, `www.shop.example` и `shop.example` — один сайт, а `a.github.io` и `b.github.io` — два.

**Размещайте сервер shopmcp на поддомене магазина** (`server.public_url = "https://mcp.shop.example/mcp"` для `shop.example`). Тогда кука всегда уходит вместе с POST.

Живая проверка V1 (15.10.2026, локальный стенд Shop-Script, Chromium; корзина из трёх позиций добавлялась в корзину покупателя, где уже была другая позиция):

| Сервер | Кука корзины магазина | Исход |
|---|---|---|
| поддомен магазина (тот же сайт) | любая | Корзина собирается, прежние позиции сохраняются |
| чужой сайт | `SameSite=None` (Webasyst на HTTPS) | То же: корзина собирается, прежние позиции сохраняются |
| чужой сайт | `Lax` (магазин по http; InSales — по разведке, вживую не проверен) | Корзина **подменяется**: каждый POST заводит новую корзину, остаётся только последняя позиция. Страница при этом доходит до `finish_url`, и покупатель ошибки не видит |

Возраст корзины и куки роли не играл. Режим `single` вживую не гонялся: правило для InSales (с чужого сайта корзина заменяется) опирается на разведку.

Не проверено: настоящий HTTPS в браузере (кука `SameSite=None; Secure` проверена подменой атрибута на локальном стенде), Safari, InSales на живом магазине. Поэтому `form_post` остаётся **БЕТА**, а пресеты InSales и Shop-Script по умолчанию дают `link_list`.

`shopmcp check` применяет эту таблицу как C11 (см. [conformance.md](conformance.md#как-c11-оценивает-form_post)): провал там, где корзина подменилась бы, предупреждение там, где всё зависит от куки магазина.

Scaffold кладёт то же предупреждение комментарием рядом с блоком `form_post`; для магазина на http добавляется, что `form_post` работает только с поддомена магазина.

## Заметки по движкам

- **Shopify** публикует собственный MCP магазина, поэтому адаптера каталога нет. Инструменту корзины всё равно нужен каталог для сверки id, так что в `[adapter]` идёт фид Google Merchant. Atom-фид с пространством имён `s:` и без `g:` отклоняется целиком. Id в ссылке корзины — `variant_id`, его `cart_ref.pattern` берёт из `g:id`.
- **WooCommerce**: каталог — снимок публичного Store API, см. [adapters.md](adapters.md#адаптер-woocommerce). Ссылка-добавление работает на любой версии.
- **Ecwid**: корзину из фрагмента URL читает скрипт витрины. Формат фида Ecwid и вариант `Wix` взяты из документации и живьём не проверены.
- **Битрикс**: ссылка-добавление кладёт одну позицию; `id` — торговое предложение.
- **Tilda**: корзина живёт в браузере. Сниппет в блоке T123 даёт корзину одной ссылкой (`url_template` с `#mcpcart=…`, без подписи).
- **OpenCart**: YML модуля бывает в `windows-1251`.
