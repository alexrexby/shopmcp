# Токен корзины и контракт приёмника

[English](../en/cart-receiver.md) · **Русский**

Для кого: автор модуля на стороне магазина (Битрикс, OpenCart, PrestaShop, Magento, Shop-Script), который принимает ссылку на корзину от shopmcp и наполняет корзину покупателя. Тот же токен несёт в своём URL страница-трамплин `form_post`.

Зачем вообще токен: сервер не хранит корзин. Вся передача живёт в ссылке, поэтому её нельзя подменить и у неё есть срок. Токен — **не** JWT: модуль проверяет его через HMAC-SHA256 и сравнение за постоянное время, без библиотек и без выбора алгоритма.

## Формат

```
<b64url(payload_json)>.<b64url(HMAC-SHA256(secret, b64url(payload_json)))>
```

- `b64url` — base64url (RFC 4648 §5) **без** паддинга `=`.
- MAC считается по ASCII-тексту первой части, а не по раскодированному JSON: JSON заново не сериализуется.
- Длина токена — не больше 1800 символов.

Полезная нагрузка:

```json
{"v":1,"kid":"1","s":"<id магазина>","iat":1760400000,"exp":1760486400,"jti":"<16 случайных байт, b64url>",
 "l":[["<product_id>","<variant_id или null>","<количество десятичной строкой>",{"<опция>":"<значение>"}]]}
```

| Поле | Смысл |
|---|---|
| `v` | Версия формата, `1` |
| `kid` | Id ключа: выбирает секрет, так ключ ротируется без поломки уже выданных ссылок |
| `s` | Id магазина (`id` в `store.toml`): токен чужого магазина отклоняется |
| `iat`, `exp` | Время выдачи / окончания, Unix-секунды |
| `jti` | Уникальный id токена: повторный клик по той же ссылке не должен добавить позиции дважды |
| `l` | Позиции: id товара, как его знает корзина магазина, id варианта или `null`, количество (`"2"`, `"1.5"`), опции (имя → значение; пустой объект, если опций нет) |

Id соответствуют `^[A-Za-z0-9._:-]{1,128}$`; не больше 20 опций на позицию, значения до 200 символов. Цены в токене нет никогда: магазин считает корзину сам.

## Проверка

1. Длина ≤ 1800, ровно одна `.`, обе части непустые.
2. Раскодировать первую часть, разобрать JSON, прочитать `kid`, взять его секрет (неизвестный `kid` → отказ).
3. Посчитать HMAC-SHA256 этим секретом по первой части **в том виде, как она пришла**, закодировать b64url без паддинга, сравнить со второй частью за постоянное время (`hash_equals` в PHP, `hmac.compare_digest` в Python).
4. `v == 1`, `s` равен id вашего магазина, `exp` и `iat` — целые; отказ, если `now > exp + 60` или `iat > now + 60` (60 с допуска часов).
5. Каждая позиция: id соответствуют шаблону выше, количество — положительное конечное десятичное число.

Секрет — значение переменной окружения, названной в `cart.secret` (не короче 32 байт), одинаковое на обеих сторонах.

## Поведение приёмника

Нормативно для каждого модуля:

- `GET <путь приёмника>?mcp_cart=<token>`.
- Если в запросе есть `Sec-Fetch-Dest` и он не `document` → `403`.
- Проверить токен, как описано выше.
- **Добавить** позиции в корзину сессии; никогда не заменять её.
- Запомнить `jti` в сессии: уже виденный токен повторно не применяется, покупатель просто уходит в корзину.
- Недоступный или неизвестный товар пропускается с флеш-сообщением.
- Итог — `302` на страницу корзины. Ошибка — `302` на корзину с сообщением, никогда не `500` и никогда не страница, на которой виден токен.

## Безопасность модуля

Токен подписан, но его содержимое — это id, названия и значения опций магазина: относитесь к нему как к вводу. Модуль — это PHP-код (или подобный) на стороне магазина, поэтому он обязан:

- Передавать id, опции и количества в базу только через **подготовленные выражения** с привязанными параметрами, никогда не склеивая их в SQL.
- Экранировать всё, что выводит (например, flash-сообщение, где названы id или опция из токена), через `htmlspecialchars` (или экранирование движка) для того контекста, куда вывод попадает.
- Проверять подпись **и** срок (с запасом 60 с) до чтения любой позиции; отказывать токену другого магазина и неизвестному `kid`.
- Применять `jti` **один раз**: помнить его в сессии (лучше — в хранилище использованных `jti` до `exp`), чтобы повторная ссылка не добавляла позиции снова.

Модуль, нарушающий любой из пунктов, — уязвимость магазина, а не shopmcp. Трамплину `form_post` модуль на стороне магазина не нужен; эти правила — для стратегии `receiver`.

| Случай | Вход | Ожидание |
|---|---|---|
| Валидный | токен, магазин `demo`, now = `1760400100` | принят; позиции `1001`/`2002` × 2 и `77` × 1.5 с опцией `Размер` = `M` |
| Просрочен | токен, now = `1760486461` (`exp` + 61) | отказ: просрочен (`1760486460` ещё принимается) |
| Чужой магазин | токен, магазин `other` | отказ: чужой магазин |
| Испорчена подпись | токен с изменённым последним символом | отказ: неверная подпись |
| Неизвестный ключ | токен, настроен только `kid` `"2"` | отказ: неизвестный id ключа |

Проверить MAC без нашего кода:

```sh
printf %s 'eyJ2Ijox…XX0' | openssl dgst -sha256 -hmac 'test-secret-0123456789-abcdefghij' -binary \
  | openssl base64 -A | tr '+/' '-_' | tr -d '='

```

## Чего подпись не даёт

Подпись доказывает, что список выдан этим сервером, не изменён, не просрочен и предназначен этому магазину. Она **не** мешает переслать валидную ссылку на корзину кому-то другому: инструмент корзины публичный, подписанную ссылку получит кто угодно. От страницы, которая молча наполняет корзину посетителя, приёмник защищают `Sec-Fetch-Dest: document` (переход верхнего уровня, а не картинка или фрейм), лимиты на позиции и количества, приём только активных товаров и `jti`.
