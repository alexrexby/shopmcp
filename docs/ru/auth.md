# Авторизация: гибридный доступ и OAuth resource server

[English](../en/auth.md) · **Русский**

Зачем доступ гибридный, одной строкой: смотреть каталог можно без аккаунта, историю заказов — нет. См. [design-notes.ru.md](../design-notes.ru.md).

## Модель

- **Публичные инструменты** (каталог, ссылка на корзину, сведения о магазине, пункты выдачи) работают без токена.
- **Персональные инструменты** требуют токен со scope. Сейчас во фреймворке это `orders_history`, scope по умолчанию `orders.read`; он существует, только если адаптер объявил capability `orders`. Адаптер `yml` её не объявляет, поэтому у магазина на `yml` персональных инструментов нет и защищать авторизации нечего.
- **shopmcp — только resource server.** Он не выдаёт токены и не имеет эндпоинтов `/authorize` и `/token`. Токены выдаёт собственный сервер авторизации магазина (`auth.issuer`); сервер проверяет их по открытым ключам этого сервера (`auth.jwks_uri`).
- Решение принимается на каждый вызов инструмента, а не на весь эндпоинт: `initialize`, `tools/list` и вызовы публичных инструментов проходят без токена. Персональный инструмент виден в списке как все остальные и отказывает при вызове без токена.
- В instructions сервера модели сказано, что делать при `401`: попросить покупателя войти через клиент и повторить вызов, данные аккаунта не запрашивать (текст `instructions.sign_in`, см. [configuration.md](configuration.md#texts)).

## Конфигурация

```toml
[server]
public_url = "https://mcp.shop.example/mcp"   # одновременно обязательная аудитория токена

[auth]
enabled = true
issuer = "https://auth.shop.example"
jwks_uri = "https://auth.shop.example/.well-known/jwks.json"
[auth.tool_scopes]
orders_history = ["orders.read"]
```

| Поле | Назначение |
|---|---|
| `auth.enabled` | `false` (по умолчанию): проверки нет совсем. `true` требует `issuer` и `jwks_uri` |
| `auth.issuer` | Ожидаемый `iss`, сравнивается как точная строка в том виде, как вы её записали |
| `auth.jwks_uri` | Откуда берутся ключи подписи |
| `auth.tool_scopes` | Scope по инструментам, см. ниже |
| `server.public_url` | `aud` токена должен ему равняться; он же публикуется как `resource` в метаданных |

При `enabled = false` нет ни шлюза, ни маршрута метаданных. Персональный инструмент, оставшийся в списке, сам отказывает при вызове с ошибкой `unauthorized`, потому что до него никогда не доходит токен; включите авторизацию или не объявляйте capability `orders`.

## Scope на инструмент

У каждого инструмента в коде есть scope по умолчанию; пустой список означает «публичный». `[auth.tool_scopes]` переопределяет их по суффиксу инструмента (часть имени после `<prefix>_`).

- `orders_history = ["orders.read"]`: умолчание, записанное явно.
- `orders_history = ["orders.read", "profile"]`: требуются все перечисленные scope.
- `products_search = ["catalog.read"]`: делает публичный инструмент персональным.
- Пустой список недопустим; чтобы убрать инструмент из магазина, используйте `tools.disabled`. Сделать персональный инструмент публичным через `tool_scopes` нельзя.
- Ключ, не являющийся суффиксом инструмента фреймворка, роняет старт (`auth.tool_scopes: unknown tools [...]`), так что опечатка не оставит настоящий инструмент на scope по умолчанию.
- Scope — это токен по RFC 6749: без пробелов, кавычек и обратных косых черт.

Набор scope публикуется и как `scopes_supported` в метаданных, а инструменты, ставшие персональными, названы в instructions сервера.

## Что сервер проверяет в токене

Токен `Bearer` должен быть JWT и пройти все проверки:

| Проверка | Правило |
|---|---|
| Алгоритм | Только асимметричные: принимаются `RS256` и `ES256`. `none` и `HS*` отклоняются до поиска ключа |
| Подпись | Ключом из `jwks_uri`, выбранным по `kid` токена |
| `iss` | Равен `auth.issuer` |
| `aud` | Равен `server.public_url` |
| `exp` | Обязателен, допуск на расхождение часов 30 секунд |
| Scope | Из `scope` (строка через пробел) или `scp` (список); нет claim — нет scope |
| Клиент | Один из `client_id`, `azp`, `sub` должен быть строкой |

Эксплуатационные детали:

- Набор ключей кэшируется на 5 минут; неизвестный `kid` вызывает повторную загрузку не чаще раза в 30 секунд. Запрос JWKS обрывается через 5 секунд.
- Если JWKS недоступен, токены отклоняются (fail closed), а повторная загрузка не выполняется 10 секунд.
- Проверка идёт в небольшом отдельном пуле потоков, так что медленный JWKS не тормозит поиск по каталогу.
- Токен, не прошедший любую проверку, считается отсутствующим. Для публичного инструмента это ничего не меняет: случайный битый токен публичный вызов не ломает.
- Проверка токена входит в лимит запросов, как любой запрос.

## Что видит клиент

Вызов персонального инструмента без токена получает `401`, с токеном без нужного scope — `403`. В обоих случаях в `WWW-Authenticate` есть адрес метаданных и scope, чтобы клиент мог начать OAuth-процедуру:

```text
HTTP/1.1 401 Unauthorized
www-authenticate: Bearer error="invalid_token", error_description="Authentication required", resource_metadata="http://localhost:8001/.well-known/oauth-protected-resource/mcp", scope="orders.read"

{"error": "invalid_token", "error_description": "Authentication required"}
```

```text
HTTP/1.1 403 Forbidden
www-authenticate: Bearer error="insufficient_scope", error_description="Required scope: orders.read", resource_metadata="http://localhost:8001/.well-known/oauth-protected-resource/mcp", scope="orders.read"

{"error": "insufficient_scope", "error_description": "Required scope: orders.read"}
```

Метаданные по [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) публичны и лежат по адресу `/.well-known/oauth-protected-resource<server.path>`:

```json
{"resource":"http://localhost:8001/mcp","authorization_servers":["https://auth.mini.example/"],"scopes_supported":["orders.read"],"bearer_methods_supported":["header"]}
```

Обратите внимание на завершающий слэш: URL в метаданных нормализуются, а проверка `iss` использует `auth.issuer` ровно так, как он записан. Если ваш сервер авторизации публикует issuer без слэша, пишите его в конфиге без слэша.

Шлюз читает тело запроса, чтобы найти имя инструмента, — и у одиночных сообщений, и у пакетов. Тело больше 256 КиБ отклоняется с `413` ещё до сервера.

## Ручная проверка

[Проверка C13](conformance.md#проверки) контролирует сторону без токена: `401` с `resource_metadata` и `scope`, метаданные называют публичный URL, публичный инструмент отвечает без токена. Валидный токен она не отправляет. Чтобы проверить авторизованный путь, возьмите токен у своего сервера авторизации и вызовите инструмент:

```bash
curl -s -X POST https://mcp.shop.example/mcp \
  -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -H "authorization: Bearer $TOKEN" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"shop_orders_history","arguments":{}}}'
```

Три исхода выше (401, 403, прохождение шлюза) прогнаны на тестовом сервере со сгенерированной парой ключей и локальным JWKS: токен с `orders.read` дошёл до адаптера, токен с другим scope получил `403`. Что смотреть в первую очередь при сбое: `aud` не равен `public_url`, `iss` отличается от `auth.issuer` хотя бы символом, токен подписан `HS256` или иным алгоритмом, кроме `RS256`/`ES256`.

## Ограничения

- Принимаются только `RS256` и `ES256`; список алгоритмов не настраивается.
- Без `orders` в адаптере (а так у всех адаптеров репозитория сегодня) персональных инструментов нет, и C13 пропускается.
- Фреймворк не сопоставляет токен с покупателем в магазине: адаптерный `orders(token, page, limit)` получает проверенный `AccessToken` (subject, scope, все claims) и сам решает, чьи заказы вернуть.
- Эшелонированная защита: `orders_history` ещё и сам отказывает (`unauthorized`), если вызов дошёл до него без аутентифицированного пользователя, на случай обхода шлюза.
