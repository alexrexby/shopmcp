# Проектные заметки

Почему фреймворк устроен именно так. Выводы получены при изучении боевых MCP-серверов крупных интернет-магазинов в 2026 году. Чужих схем и данных здесь нет.

## Что берём

1. **Гибридный доступ.** Инструменты каталога (поиск, карточка, скидки, магазины, ссылка на корзину) работают без токена. Персональные (история заказов, личные предложения) закрыты OAuth 2.1. Без токена они отвечают HTTP `401` с `WWW-Authenticate: Bearer resource_metadata="…", scope="<scope инструмента>"`. Сервер публикует `/.well-known/oauth-protected-resource` по RFC 9728. Токены выдаёт сервер авторизации магазина, фреймворк только проверяет их как resource server.
2. **Передача корзины, а не оформление заказа.** Агент собирает список, сервер выдаёт ссылку, по ней корзина наполняется на сайте магазина. Оплата и оформление остаются у магазина, поэтому у MCP-сервера нет ни платёжного контура, ни PCI.
3. **Префикс бренда в именах инструментов** (`<store>_products_search`): несколько магазинов уживаются в одном клиенте.
4. **Проекция полей и явная пагинация** (`mode: short|full|custom`, `fields[]`, `has_more`) удешевляют ответы в токенах.
5. **`instructions` сервера** сообщают модели правила магазина, в том числе что делать при `401`.

## Какие дефекты не допускаем

Каждый пункт — проверка conformance: магазин, прошедший `shopmcp check`, от него свободен.

1. Бизнес-ошибки с `isError: false`.
2. HTML-сущности и разметка (`&nbsp;`, `<br>`) в тексте, который читает модель.
3. JSON с отступами тратит лишние токены. У нас компактный JSON плюс `structuredContent` и `outputSchema`.
4. Нет `annotations` у инструментов (`readOnlyHint`, `openWorldHint`).
5. Огромные первые страницы. Справочники фильтров отдаёт отдельный инструмент, у каждого ответа есть бюджет в байтах.
6. Описание инструмента противоречит схеме, например «1..20 позиций» при `maxItems: 30`. Лимиты генерируются из одной константы.
7. Необязательные фильтры объявлены как `required`.
8. Размер страницы нельзя изменить там, где это важно.
